01 · Descripción general

¿Qué es el modelo C4?

Origen. Creado por Simon Brown (2006+) como respuesta a las limitaciones de UML para arquitectura de software. Hoy es estándar de facto en la industria.

Propósito. Describir la arquitectura de un sistema de software en 4 niveles de abstracción, desde visión empresarial hasta código, facilitando comunicación entre stakeholders técnicos y no técnicos.

¿Por qué 4 niveles? Porque arquitectura no es una vista única. El contexto importa al CTO, los contenedores al DevOps, los componentes al arquitecto, el código al desarrollador.

Los 4 niveles
Level 1: Context
Sistema + usuarios + sistemas externos
Level 2: Container
Aplicaciones, bases de datos, nodos físicos
Level 3: Component
Módulos funcionales dentro de un container
Level 4: Code
Clases, funciones, métodos

Constructos y conceptos del modelo C4

ConstructoRol
SystemEl software que se describe
PersonUsuario o actor externo
Software SystemSistema externo que interactúa
ContainerAplicación, BD, nodo, microservicio
ComponentMódulo lógico dentro de un container
CodeClases, métodos, funciones
RelationshipInteracción: Uses, Sends, Calls
Restricciones (buena formación)
  • Un System contiene ≥ 1 Container.
  • Un Container contiene ≥ 1 Component (o es atómico).
  • Un Component contiene ≥ 1 Code unit.
  • Las relaciones Uses representan sincronía (HTTP, RPC).
  • Las relaciones Sends representan asincronía (MQTT, EventBus).
  • Solo se conectan elementos del mismo nivel (no Container → Code).

05 · Semántica

¿Qué significa cada nivel? (Transformación de abstracción)

1Context
¿Quiénes son los usuarios? ¿Qué otros sistemas existen? ¿Límites del sistema?
2Container
¿Qué aplicaciones/nodos/DBs hay? ¿Cómo se despliegan? ¿Tecnología base?
3Component
¿Qué módulos funcionales hay dentro? ¿Cómo se comunican? ¿Responsabilidades?
4Code
¿Qué clases/métodos implementan? ¿Patrones de diseño? ¿Detalles técnicos?
En SVIF:

Context: Usuario quiere acceder, cámara detecta, cerradura se abre.

Container: Dos nodos ESP32 (Face Monitor + Access Actuator) comunicados por MQTT.

Component: Dentro de Face Monitor: captura, detección, identificación, MQTT sender.

Code: monitorearPresenciaTask(), capturarImagen(), identificarRostro(), publicIdentificationEvent().

07 · Reflexión personal y crítica

¿Por qué C4 es útil y cuáles son sus limitaciones para CPS?

✅ Fortalezas de C4
  • Escalable. 4 niveles claros permiten comunicar desde CEO hasta desarrollador sin abrumar.
  • Agnóstico. No asume tecnología; funciona igual para Java, Node, Go, IoT.
  • Composable. Se puede expandir con diagramas adicionales (deployment, infraestructura).
  • Bidireccional. El código puede generar C4 (inversión) o C4 guiar el código (forward-engineering).
  • Comunicación. Diagramas visuales ayudan a stakeholders no técnicos a entender estructura.
❌ Limitaciones para CPS
  • No muestra tiempo. ¿Cada cuánto se ejecuta monitorear? (500 ms en SVIF) → necesita anotación.
  • No muestra transiciones. ¿Qué ocurre si authorized=true vs false? → necesita lógica de control.
  • No muestra hardware. ¿Qué pin? ¿Qué sensor? → apenas menciona HWResource.
  • No muestra restricciones temporales duras. ¿Deadline? ¿Jitter tolerable? → requiere DSL más específico.
  • Abstracción variable. Un "Container" puede ser app web o nodo ESP32 con 2KB RAM → demasiado genérico.
🔍 Reflexión: ¿C4 o DSL PIM?

C4 es excelente para arquitectura de software general. Comunica limpiamente "Face Monitor y Access Actuator son nodos separados, conectados por MQTT." Pero CPS añade requisitos que C4 no contempla: periodicidad, hardware específico, refinamientos de decisión (if authorized then unlock else alarm), trazabilidad a objetivos (iStar 2.0). Por eso en el proceso MDD4CPS, después de definir CIM (iStar) y Level 2 (C4), necesitamos un DSL PIM especializado que capture esos detalles antes de llegar a código.

Conclusión: C4 es el "contexto y contenedores"; DSL PIM es el "comportamiento y timing". Complementarios.
